# Dataset Creation Flow — Storage & Persistence Audit (DS-LAKE-001)

Read-only audit of the current Dataset Creation Flow. Identifies every persistence point, the real
storage authority, and the gaps against the target Bronze/Silver/Gold/Final Lakehouse architecture.

Source of truth for the refactor: `feature_list.preprocessing.json`.
Plan: `~/.claude/plans/claude-md-rewrite-in-feature-list-prepr-starry-pike.md`.

Every claim below was verified against the current tree. Where the refactor request and the
implementation disagree, the implementation is reported and the disagreement is named.

---

## 0. Two corrections to the refactor request

**The wizard has five steps, not six.**

`DW_TOTAL_STEPS = 5` (`apps/client/store/dataset-studio.ts:29`), five labels in
`wizard-shell.tsx:22-30`, and Save is Step 5 (`step-5-review-save.tsx`). The request's "Step 1
Connect Data Source" happens in `create-dataset-dialog.tsx:30-71` **before** the wizard mounts —
Step 1 is tag verification. The request's "Step 5 Validation" has no counterpart at all. The
six-step reading likely comes from counting Step 3's two sub-steps (3.1 EDA / 3.2 Imputation)
separately.

**TimescaleDB does not exist in this repository.**

Not an extension, not an image, not a service. `docker-compose.yml:3` is `postgres:16-alpine`.
Across all 17 migrations there are zero occurrences of `create_hypertable`, `timescale`,
`hypertable`, `continuous aggregate` or any `CREATE EXTENSION`. There is no serving layer of any
kind: every dashboard figure is either derived client-side from workspace/node rows
(`use-pipeline-analytics.ts:43-58`) or generated by `lib/mock-readings`
(`use-sensor-readings.ts:3-7`). `services/readings.ts` does not exist.

| Step 2 — Fetch Raw Data      | `step-2-raw-data.tsx:83-208` → `use-dataset-studio-fetch.ts:126` → `POST /api/v1/authorized/data-source/:id/fetch` | **read-only**                  |
| Step 3 — Data Cleaning       | `processing/step-3-1-EDA.tsx`, `step-3-2-imputation.tsx:146`                                                       | none — runs in the **browser** |
| Step 4 — Feature Engineering | `step-4-feature-engineering.tsx`                                                                                   | none — runs in the **browser** |

All Step 3 and Step 4 processing is computed client-side. `step-5-review-save.tsx:82-108`
recomputes the whole chain in a `useMemo`:

```
raw → applyFeatures → precleanse → preprocessPipelines → selectColumns → toModelReady
```

using `lib/feature-engineering`, `lib/precleanse` and `lib/preprocessing`. No server call is made
for any of it. What is saved is a **recipe** (`Dataset.pipelineConfig`), not a computed dataset.

Save is two non-atomic phases, documented as deliberate at `step-5-review-save.tsx:178-182`:

1. `datasetService.create` / `.update` → the `Dataset` row.
2. Gated on `res.data.currentVersionId === null` (`:163`) → `storeRows()` (`:183-206`) →

   warning (`:199-205`), and the dataset stays saved. Skipped entirely when
   `materializeBlocker(config)` returns a reason (`:184-188`).

## 2. Current Storage Strategy

**MinIO is already the source of truth for rows.** Postgres holds metadata and pointers only —
verified model by model: not one of the 18 Prisma models stores timeseries rows.

`apps/python` holds the **only** S3 credentials in the system. NestJS has none:
`grep -rn "MINIO\|S3_\|minio" apps/backend/src packages/common` returns nothing, and
`apps/backend/src/config/env.config.ts` exposes only `JWT_*`, `PYTHON_API_URL` and
`DATASOURCE_ENCRYPTION_KEY`. Stated explicitly at `apps/python/intergrations/object_store.py:168-171`.

Rows never pass through NestJS. `materialize` takes credentials and fetch parameters, not rows —
forwarding millions of rows as JSON would move the browser's memory ceiling onto the API server
rather than remove it.

## 3. Current MinIO Structure

Bucket `datasets` (`apps/python/config/env.py:48`, `.env.example:37`). Keys built by
`object_store.py:311-323`:

```
datasets/{datasetId}/{versionId}.parquet        committed, IMMUTABLE
datasets/{datasetId}/tmp/{jobId}/{n}.parquet    per-operation intermediates
```

Frame contract (`object_store.py:12-20`, enforced by `assert_frame_shape:104-145`):

```
timestamp        timestamp[ns], naive Bangkok local
{tag}            double
{tag}__status    int8   0=Good, 1=Bad, 2=Questionable
```

N logical tags produce 2N+1 physical columns. Parquet via `pyarrow.parquet.write_table`
(`:231`), content type `application/vnd.apache.parquet` (`:240`). `put_frame` refuses to overwrite
a committed key (`:224-228`).

**Drift:** the three key helpers are re-implemented as TypeScript template literals in three
places rather than shared — `dataset-version.authorized.service.ts:172`,
`preprocessing-job.service.ts:190-191` and `:215-217`.

**Absent today:** checksum, manifest, feature specification, validation report, and any
artifact-type dimension in the key.

### Defect 5a — `Dataset.currentVersionId` has no foreign key

`packages/prisma/prisma/migrations/20260801163509_dataset_versions_and_jobs/migration.sql:8` is a
bare `ALTER TABLE "Dataset" ADD COLUMN "currentVersionId" TEXT;` with **no matching
`AddForeignKey`**, unlike every other relation created in that same file. The Prisma model
(`schema.prisma:313`) likewise declares it as a plain `String?` with no `@relation`.

A dangling pointer today. Once promotion and lifecycle transitions exist, it becomes a genuine
integrity hazard.

### Defect 5b — `sizeBytes` is 32-bit

`DatasetVersion.sizeBytes Int` (`schema.prisma:358`) while `apps/python/services/preview_service.py:24`
documents a measured 396 MB artifact. Correct today, wrong at roughly 2.1 GB.

## 6. Current Dataset Versioning

`versionNumber` and `stage` are **conflated on one table**. `DatasetVersion.stage`
(`RAW | CLEAN | FEATURE`, `schema.prisma:320-325`) _is_ the artifact-type axis, while
`versionNumber` is the version axis. That conflation is precisely why intermediate stages create
versions.

Write points:

| Stage   | File:line                                   | Transaction                                                                           |
| ------- | ------------------------------------------- | ------------------------------------------------------------------------------------- |
| `RAW`   | `dataset-version.authorized.service.ts:187` | `$transaction` at `:181-209`, with the `Dataset.currentVersionId` update at `:204`    |
| `CLEAN` | `preprocessing-job.service.ts:290`          | `$transaction` at `:280`, with `SUCCEEDED` at `:308` and the pointer update at `:321` |

**`DatasetVersionStage.FEATURE` exists in the enum and no write path anywhere produces it.**

### Defect 6a — "version only at Save" is already violated

Opening an existing dataset in **Edit** mints a `DatasetVersion` with no save at all.

`use-dataset-edit-hydration.ts:43` calls `useDatasetVersionRows(dataset, { enabled })` — passing
only `enabled`, so `materialize` keeps its default of `true` (`use-dataset-version-rows.ts:124`).
Branch 2 of the three-branch resolution (`:219-242`) then issues `createRaw` on mount.

The only caller that opts out is `models/create/components/pipeline/phase-3-evaluation.tsx:87`,
which passes `{ materialize: false }`.

Three-branch hydration, documented verbatim at `use-dataset-version-rows.ts:16-35`:

1. `currentVersionId` set → page the committed artifact, preferring the earliest `RAW` version
   (`resolveVersionId:195-207`).
2. No version, recipe replayable → materialise V1 on demand.
3. Neither → `buildRawDataset` synthetic rows **with a visible reason**, surfaced by
   `SyntheticDataBanner` (`wizard-shell.tsx:155-157`).

`materializeBlocker` (`:76-108`) refuses replay when `baseTags` or `customDateRange` are missing,
when there are zero or more than one source, for `csv` sources, and for any non-`pi` type.

## 7. Current Model Flow (and the one coupling that constrains this refactor)

Datasets and Models are independent in the direction that matters: saving a Dataset never creates
a Model. `prisma.model.create` appears exactly once, at
`api/v1/model/authorized/model.authorized.service.ts:158`.

The coupling that does constrain the refactor is a **read**:
`phase-3-evaluation.tsx:87` resolves rows through `useDatasetVersionRows` against
`Dataset.currentVersionId`. The refactor's own checklist requires "Model Training still works
without modification", so `GET /:id/versions/:versionId/rows` must keep resolving.

Out of scope but recorded: the Model row is INSERTed at **Step 2, not Step 4** —
`use-model-training.ts:56` `await commit()` → `use-model-commit.ts:81` `createModel`, while
`phase-4-deploy.tsx:42` re-calls the same `commit()` and takes the `updateModel` branch. Tracked by
`docs/feature_list.json` MODEL-FLOW-003 / MODEL-FLOW-007 and detailed in `docs/MODEL_FLOW_AUDIT.md`.

`datasetVersionService.preview()`, `.clean()`, `.job()`, `.cancelJob()` and `.retryJob()`

**This is the core of the refactor: wiring, not building.**

## 9. Background job architecture

No queue infrastructure exists. Verified by grep for `bullmq|ioredis|redis|celery|@nestjs/schedule|node-cron|new Worker|Queue(`
across `apps/` and `packages/`: the only hits are comments in `preprocessing-job.service.ts:21,56`
**stating the absence**, plus UI polling `setInterval` timers. `REDIS_URL` appears in
`.env.example:28` but is absent from `.env`, with nothing running.

What exists instead is an in-process runner
(`api/v1/dataset-version/authorized/preprocessing-job.service.ts`, registered as a plain provider):

- `start(jobId)` is fire-and-forget; the caller has already answered `202`.
- One `postToPython('/v1/preprocess/clean')` **per operation**, chaining `sourceKey → targetKey`
  through `tmp/{jobId}/` (`:206-242`). Only the last operation writes the committed key
  (`:215-217`).
- Commit is a single `$transaction` (`:268-326`), with `versionNumber` read **inside** the
  transaction so concurrent jobs cannot collide on `@@unique([datasetId, versionNumber])`.
- Cancellation via an in-memory `Map<string, AbortController>` (`:80`), necessarily empty at boot.
- `onModuleInit` (`:102-116`) sweeps every `RUNNING` row to `FAILED`.

**Single-replica assumption**, documented at `:51-57`: with two replicas, one instance's boot
sweep would kill the other's live jobs. The stated escape hatch is
`SELECT … FOR UPDATE SKIP LOCKED` with an owner column — still no Redis.

## 13. Rule Book conflict (surfaced per CLAUDE.md §1, not absorbed)

`docs/ARCHITECTURE.md` and `docs/CODEBASE.md` contain **zero** mentions of `apps/python`, MinIO,
S3, object storage, Parquet, `Dataset`, `DatasetVersion`, `PreprocessingJob`, queues or background
jobs. `docs/ARCHITECTURE.md:216-226` lists core Prisma models and omits `Dataset`,
`DatasetVersion`, `PreprocessingJob`, `DataSource`, `WorkspaceMember` and `Edge`.
`docs/CODEBASE.md:179-213` ("Active Endpoints") lists none of the dataset, dataset-version,
data-source or model endpoints, all four of which exist.

Both Rule Books are accurate and authoritative for the NestJS / Next.js / Prisma layers. They are
stale with respect to the entire data and storage layer. Updating them is worthwhile but is
documentation work outside this refactor; it is recorded in the ledger's `deferred[]`.

A second, narrower conflict: `docs/SECURITY.md:50` mandates a global `ValidationPipe` with
`whitelist: true, forbidNonWhitelisted: true`, while `docs/CODEBASE.md:232` states the pipe is not
globally active. Unrelated to this refactor, recorded so it is not lost.
